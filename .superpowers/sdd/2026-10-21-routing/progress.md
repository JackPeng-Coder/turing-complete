# 账本：排线路由的实验性改进（2026-10-21）

用户贴了一张 896 门沙盒电路的截图，并说：

> 大型电路的排线实际上是极其混乱的，请你进行实验性改进，尝试改进排线的算法

截图里 I/O 面板只有 `IN_1`、`IN_2`、`OUT_1` 三个连接器，但板上有 896 个与非门——也就是
两条输入网各扇出到几百个输入脚（`IN_1` 走偶数行、`IN_2` 走奇数行），这是"排线混乱"的根源：
几百条属于同一个信号的线被各自独立地到处拖，长线穿过门体，同一条线上叠着不同网的线。

**这件事没有基准电路可拿**：用户那块板只存在于他的浏览器里（`tc.sandbox.v1`），截图之外
拿不到图数据。所以实验用两块**生成的**压测板，形状按截图构造：

| 板 | 形状 | 规模 |
|---|---|---|
| `chain` | 网格化的随机逻辑：每个门由上一行两个门驱动，另加 1/3 的长线 | 896 门 / 1923 线 |
| `fanout` | 截图的样子：16 行 × 56 列的门排成行，两个连接器各扇出到一半行；行内门链相连 | 899 门 / 1798 线 |

质量指标（全部由 `planRoutes` 的 polyline 事后测量，脚本在实验期是临时文件；固化的部分在
`test/ui/route-quality.test.ts`）：

- `partHits`：线段落在门体内部的长度（缩进 1px，避免把"接到门边"算进去）；
- `crossings`：不同线之间的垂直交叉点数；
- `exactOverlap` / `closeOverlap`：不同网上线段重合（间距 < 1 / < 8）的长度；
- `sameNetParallel`：同网线段并行（< `WIRE_CLEARANCE`）的长度，扇出成束时应该上升；
- `planMs`：一次全量规划耗时（只有电路变化才重算；平移、缩放走缓存）。

## 裁决

| # | 裁决 | 理由 / 代价 |
|---|---|---|
| 1 | **同一网络的并行不计费，也不同向计费**（`costOf` 里 `p.net === net` 直接跳过） | 从同一个输出脚引出的多根线**就是同一个信号**：叠在一条线上是正确的画法，不是短路。旧路由器把每条线都当成独立的网，扇出因此被"撑开"成一片扇子；免费之后它们会汇成主干再分叉。 |
| 2 | **每条已放线段按"网"计一次，而不是按"线"计一次**（`LaneIndex` 在 `add` 时按 net 合并区间） | 扇出主干在同一车道上可能有几十条线，但画面上**只有一条线**。旧实现让下一条线为这几十条各付一次钱（`5 亿像素`级别的罚分），于是它宁愿从门体里穿过去——这就是压测里 763k 像素穿门的主因。按网计一次之后同一块板穿门降到 0。 |
| 3 | 每条部件边给**两条候选轨道**（`lane` 与 `lane + WIRE_CLEARANCE`），起点/终点列也加轨道，纵排线的"入口列"与"出口列"各加一个变体 | 门与门之间的空隙恰好只有一个 `WIRE_CLEARANCE` 宽，旧候选集每个空隙只有一条合法坐标。两条网的自然车道撞在一起时，没有第二条合法轨道可退，只能叠着画。轨道把"并排"变成可行解。 |
| 4 | `parallel` 罚分 **120 → 24** | 旧值与"按线计"叠加后，拥挤车道的代价远高于穿一个门体（400/px），所以路由器在密板上选择"打洞"。按网计一次之后，24/px 已足以让两条不同网拉开一个轨道，同时让"绕行"重新便宜于"穿门"。 |
| 5 | `MAX_LANES` **16 → 14**（每条方向最多评估 14 条候选车道） | 候选集翻倍（多了轨道与两种竖排变体）后，性能直接与这个数线性相关。14 是压测板上的拐点：16 几乎不再改善、10/12 会让同线重叠从 2 千像素级暴涨到 31 万像素级（`test/ui/route-quality.test.ts` 的小板上实测）。 |
| 6 | **交叉仍然不计费** | 保持原设计：这是两张网的正常相遇，计费需要全局扫描，代价不成比例。压测里 fanout 板的交叉数反而从 195k 降到 134k；chain 板从 23.7k 微升到 24.1k（多出来的候选偶尔换来一条交叉更多的近路），记录在案。 |
| 7 | `bend` 成本改为**数真实拐角**（`cornersOf`），而不是 `points.length - 2` | 旧式把同一方向的两个冗余点也算成弯（x 族每条约 4 个弯而非 2 个），使两个族的弯成本被抹平。属于顺带修正，单独测得的收益很小，但让权重表与画面一致。 |

## 实验记录（尝试过但没留下来的）

| 实验 | 结果 |
|---|---|
| `MAX_LANES` 16 → 32（只加车道） | 穿门 59.7k → 70.2k、耗时 +20%：候选变多但没有区分网络，几乎没有收益。 |
| 只修 `cornersOf` | 指标几乎不变（96% 的候选在同一族内比较，弯成本是常数差）。 |
| 同网并行**奖励**（`reuse = 0.8/px`） | 奖励无上限，叠在一条拥挤主干上能"赚"回 50 万像素罚分，路由器因此更愿意穿门（fanout 穿门 763k → 449k，但仍远高于免费方案）。撤销，改成"免费"（0）。 |
| 同网免费 + 逐网聚合 + 两条轨道 | 决定性的组合：fanout 穿门 763k → **0**，同线重叠 15.1M → 0.86M；chain 穿门 59.7k → 13.7k。 |
| 竖排"主干列"变体（`start.x + WIRE_CLEARANCE`） | 不同网同线重叠 50M → 107k（两块连接器叠在左列时，两条主干不再共用 x=88 这一列）；交叉数上升，但相对旧路由器仍是下降的。保留。 |
| 竖排"下降列"变体（`end.x - WIRE_CLEARANCE`） | 同线重叠 158k → 13k；fanout 耗时 +15%、chain +40%。保留——它消掉的是"看起来短路"的那一类。 |
| `parallel` 60 / 24 / 12 | 60 与 24 结果接近；12 开始把同线重叠拉回百万像素级。取 24。 |
| `MAX_LANES` 10 / 12 / 14 / 16 | 12 及以下质量塌方（小板同线重叠 31 万 px）；14 与 16 质量接近、14 快约 15%。取 14。 |

## 最终测量（同一台机器、同一组板、最终代码）

| 指标 | chain 旧 → 新 | fanout 旧 → 新 |
|---|---|---|
| 穿门长度 `partHits` | 59,698 → **0**（172 条线 → 0 条） | 772,380 → **0**（497 条线 → 0 条） |
| 不同网同线重合 | 926,188 → 847,972 | 15,070,388 → **13,232**（−99.9%） |
| 不同网并行（<16px） | 1,299,324 → 1,115,016 | 15,763,684 → **44,952**（−99.7%） |
| 同网并行（成束量） | 168,312 → 439,700 | 43,915,536 → **199,664,200**（4.5×） |
| 交叉点 | 23,676 → 24,074 | 195,367 → **134,165**（−31%） |
| 总长度 | 1,250,572 → 1,209,676 | 3,789,884 → 3,777,820 |
| 拐角数 | 7,544 → 8,010 | 6,293 → 6,921 |
| 全量规划 `planMs` | 280 → ~630（2.2×） | 525 → ~660（+26%） |

小规模回归（`test/ui/route-quality.test.ts`，240 门 / 480 线的扇出板）：穿门 6,650 → 0，
不同网同线 533,372 → 2,184（阈值 5,000）。旧路由器在这两条断言上失败，新路由器通过——
测试不是空转。

**性能的代价要如实记下**：候选集从 32 条变成 56 条，`costOf` 对每条候选都要扫附近门体，
所以大板的全量规划慢了一倍左右（chain 板最明显）。这是"只有电路变化才重算"的那一档：
平移、缩放、悬停都不重算（`planRoutes` 按图指纹缓存）；拖一个元件时每帧重算，896 门的板会
掉到 1–2 fps——与旧路由器同一量级（旧代码在这块板上也已经 ~2–4 fps），但确实更慢。要换性能
就调 `MAX_LANES`，账本里记了 12 以下的质量塌方作为下限。

## 证据

- `test/ui/route-quality.test.ts`（新增，3 条）：大板"没有线穿门"、扇出板"不同网不共线"
  （阈值 5,000，旧代码 533,372 失败）、"同网成束 > 100,000"。
- `test/ui/routes.test.ts` 原有 7 条（穿门、车道间距、稳定性、预算）全部通过——稳定性
  （"新线不会移动已有的线"）没有被破坏：规划顺序仍是玩家画线的顺序。
- 全量门禁：`pnpm build` exit 0（89 模块，300.30 kB / gzip 102.96 kB）、
  `pnpm test` **69 文件 / 1738 用例全通过**（基线 68 / 1735）、
  `pnpm smoke` **34 通过 + 2 跳过（38.6 s）exit 0**。

## 已知限制 / 没做的

- 用户那块真实电路拿不到，压测板是**按截图构造**的；指标对"形状相同"的板可靠，对具体那一块
  只能间接推断。截图之外的字体/配色问题不在本轮。
- 小板（`route-quality` 的 240 门板）仍有 ~2k 像素的不同网共线：车道数量在密集板上是硬约束，
  候选再多也有躲不开的时候；阈值把这类残余钉在旧量级的 1% 以内。
- 交叉点没有成为优化目标（裁决 6）。若以后要"更少的交叉"需要全局代价，那是另一个算法。
- 大板拖拽性能见上：这是候选集扩大的直接代价，账本留了旋钮。
