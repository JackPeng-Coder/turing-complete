## 5. Self-review findings (brief-vs-reality conflicts)

I read my own diff line by line and re-ran every acceptance command. Four deviations from the
brief's literal text were unavoidable; each is listed with its evidence, and two of them
(`B`, `C`) were required for the brief's own acceptance criterion `pnpm build` to pass.

### Conflict A — `jsdom@28.0.1` does not exist (substituted `28.1.0`)

`pnpm install` failed with `ERR_PNPM_NO_MATCHING_VERSION`. I verified against **both** the
configured mirror (`registry.npmmirror.com`) and upstream (`registry.npmjs.org`): jsdom's 28.x
line contains `28.0.0` and `28.1.0`, not `28.0.1` (latest overall is `30.1.1`). All four other
pins exist exactly as written and are used verbatim: `vite@8.3.1`, `vitest@5.0.2`,
`typescript@5.9.3` (TS 7.x deliberately not taken, per the brief's note), `@playwright/test@1.63.0`.

I tried to ask rather than guess, but human interaction is unavailable to me
(`ask_user_question` → "human interaction is unavailable while the calling agent is owned by
another live agent"), so I took the smallest possible step: `28.1.0`, the newest existing
release in the brief's intended 28.x line. **Lead: if you prefer `28.0.0` or the current
`30.1.1`, it is a one-line change plus `pnpm install`.**

### Conflict B — the brief's `vite.config.ts` cannot typecheck (added a 1-line type reference)

`pnpm build` runs `tsc --noEmit`, and `tsconfig.json` includes `vite.config.ts`. As written, the
build failed:

```
vite.config.ts(6,3): error TS2769: No overload matches this call.
  Object literal may only specify known properties, and 'test' does not exist in type 'UserConfigExport'.
```

Vite's `defineConfig` does not know about `test` unless Vitest's module augmentation is loaded.
Fix (one added line, brief's import line untouched):

```ts
/// <reference types="vitest/config" />
import { defineConfig } from 'vite';
```

Verified: `vitest/config` really does declare `module "vite" { interface UserConfig { test?: VitestInlineConfig } }`
(`node_modules/vitest/dist/config.d.ts:28-34`), and `pnpm build` passes with the reference.

### Conflict C — `environmentMatchGlobs` was removed in Vitest 5 (replaced with per-file docblocks)

This is the most consequential finding and it **corrects a preflight row** in the SDD ledger
("1 → all … jsdom only under `test/ui/**` … No change"). The brief's key does not work at all in
Vitest 5:

1. **Runtime: silently ignored.** A probe test at `test/ui/` asserting `typeof document === 'object'`
   failed with `Received: "undefined"` while the brief's key was in place. No warning, no error —
   the string `environmentMatchGlobs` does not appear anywhere in `node_modules/vitest` (0 matches).
2. **Typecheck: rejected.** After Conflict B was fixed, `pnpm build` failed with
   `vite.config.ts(36,11): error TS2769: … 'environmentMatchGlobs' does not exist in type 'InlineConfig'`.

So the brief's config could not survive `pnpm build`, and its documented intent ("opt `test/ui/**`
into jsdom by directory") was a no-op regardless. I therefore replaced it with Vitest 5's
supported opt-in — `// @vitest-environment jsdom` as the first line of a test file — and verified
both directions (probe passes with the docblock; `document` is `undefined` without it).

Why this is safe for the plan, not just for Task 1: the phase-0 plan's **only** DOM test already
declares that docblock — plan line 5360, `test/ui/panels.test.ts`, `// @vitest-environment jsdom`.
The net effect on Task 11 is therefore *better* than the preflight assumed: `test/ui/panels.test.ts`
still gets jsdom, while `test/ui/view.test.ts` (documented as DOM-free geometry, plan line 4433)
now runs on node instead of paying for jsdom.

Alternative considered and **rejected with evidence**: Vitest 5's other supported replacement,
inline `test.projects` with a `node` project and a `jsdom` project for `test/ui/**`. I implemented
it and ran it — with `extends: true` the root `include` leaks into the child project and the suite
ran **twice** (output: `✓ |node| test/smoke/sanity.test.ts` and `✓ |ui| test/smoke/sanity.test.ts`,
`Tests 2 passed (2)`); dropping `extends` means duplicating `globals` per project and introduces
empty-project edge cases, and it would also make `passWithNoTests` (`tsc`: "does not exist in type
`Omit<InlineConfig, NonProjectOptions …>`") necessary. That is materially more config machinery and
more risk than the plan needs, so I kept the config minimal and honest. If phase 1 wants genuine
directory-wide mapping later, `projects` is the path — with the root `include` removed.

The reasoning is recorded in the file itself (`vite.config.ts:12-20`) so the next implementer is
not surprised, and a UI test that forgets the docblock fails loudly with `document is not defined`
rather than silently running in the wrong environment.

### Conflict D — pnpm 11 generated `pnpm-workspace.yaml`; committing it is required for reproducible installs

`pnpm install` created `pnpm-workspace.yaml` containing `minimumReleaseAgeExclude` for

This host has a minimum-release-age policy active, and the pinned `vite@8.3.1` / `vitest@5.0.2`

failure whose message blames the lockfile. Verified: restored file → `--frozen-lockfile` exit 0,
and a full `git clone` → install → test → build cycle passes end to end.
