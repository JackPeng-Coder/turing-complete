### The fix (brief deviation, 2 lines)

I kept the level data verbatim and seeded the walk with the *starter palette* — plumbing plus the two constant sources — instead of weakening or deleting the assertion. The reasoning: the rule the brief states in prose ("a level only offers parts the player already has") is what matters, and level 1's palette *is* what the player starts with. The seed is now a named, documented constant so the exception is auditable rather than smuggled into a literal:

```ts
const STARTER_COMPONENTS: readonly string[] = [
  'level_input', 'level_output', 'const_on', 'const_off',
];
...
const unlocked = new Set<string>(STARTER_COMPONENTS);
```

Plus a new assertion pinning it down, so the seed cannot be widened silently:

```ts
it('starts the player on exactly the level-1 palette', () => { … });
```

## Issues and concerns

1. **[Cross-task, must be fixed in Task 10/11] The constants are not in the "always available" set, so level 1 would be unplayable in the app.** `src/app/progress.ts` (plan Task 10) derives `unlockedComponents` as `PLUMBING` (`['level_input','level_output']`) plus rewards of *passed* levels, and `paletteDefsFor` filters `level.allowedComponents` through it. With `emptyProgress()`, level 1's palette is therefore `['level_input','level_output']` — nothing that can drive an output — even though its briefing says "the palette has Constant On and Level Output". The plan's own test expects `paletteDefsFor(emptyProgress(), levels, other)` to equal `['level_input','level_output']`, and the plan's problem list claims derived unlocking solved "level 1 is unbuildable", which it does not. **Remediation:** treat the two constant sources as starter parts, e.g. `export const PLUMBING = ['level_input','level_output','const_on','const_off'] as const` (and update that expectation), or have `paletteDefsFor` union level 1's own `allowedComponents`. Task 12's smoke test builds level 1 through the palette and will fail otherwise. This task's test documents the requirement in `STARTER_COMPONENTS`; the level layer has no field that can express "starter" (rewards are granted only on completion), so my test is the only place I could fix it.
2. **[Data, kept verbatim] Level 6's `threeStar` is loose:** `gate: 4, delay: 3` exactly matches the NAND-only NOR route (`NOT,NOT,NAND,NOT`, verified 4/3, 3 stars) but the OR+NOT reference beats it at 2/2. It is reachable, so the rule "the reference must achieve the target" holds; I kept the brief's value because it describes the harder intended route. Tightening it to `2/2` is a judgement call for the reviewer, not a correctness fix.
3. **[Data, kept verbatim] Level 6's `rewards` re-list `const_on`/`const_off`**, which level 1 already needs. Harmless (a set add) and deliberately preserved because plan Task 9's level 7 (`ch1-07-always-on`) offers `const_on` and its gating walk must find it unlocked by then.
