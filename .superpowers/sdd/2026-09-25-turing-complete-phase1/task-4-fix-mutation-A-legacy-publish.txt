--- COUNT RECONCILIATION: THE TEST THAT DIFFERS (settled after the run above) --------------
The single test that accounts for the old logs' "138 tests / net 52" versus the final tree's
"139 tests / net 53" is

  test/core/net.test.ts > wide storage > publishes a multi-byte storage def through the same path

-- the 12-bit `reg12` holder with TWO state bytes, which was added to `net.test.ts` AFTER the old
mutation runs and BEFORE the old GREEN run (hence mutation A's report line claiming "139 passed"
while its own log said 138).

How that is known, from the logs rather than from memory: the four pre-commit logs that cover the
52-test tree (task-4-red-1, task-4-red-2, task-4-mutation-B, task-4-mutation-C) are all VERBOSE --
129..157 per-test lines each -- and the string "multi-byte" occurs ZERO times in all four, while
"publishes a 1-bit storage def across a pin an instance widened" occurs exactly once in each. So
the widened 1-bit test was already in the 52-test tree and the 12-bit one was not. (The other
candidate the review named is therefore ruled out, not merely deprioritised.)

Is the extra test discriminating for this mutation? NO -- it is indifferent to A, B and C, which is
why its absence did not change any of the three verdicts. Shown two ways: it is run alone under
this same mutation above and passes (exit 0), and by construction -- it registers its own `reg12`
def, so no shipped def's publish body is in the picture at all, and every assertion of it is read
after a settle, which republishes through `evaluate` whatever the pass did or failed to do.
